# 管理端协作约定

三人的开发主责见[分工清单](docs/team/分工与验收清单.txt)。本文件说明如何把各自成果合并到同一个仓库。

## 开始修改

从最新 `main` 创建一个职责明确的分支，例如：

```bash
git switch main
git pull --ff-only
git switch -c feat/recording-review
```

可使用 `feat/admin-data`、`feat/stats-export`、`docs/interface-contract` 等名称。分支和模块对应即可，不需要每个人长期维护一套独立主分支。

当前 `server.py` 与 `app.js` 同时包含多个模块。修改前在组内说明范围；如果要拆分文件，先约定公共接口，再提交结构调整。接口字段的改变同步更新 `docs/api/`，避免页面、统计和导出使用不同语义。

## 提交与合并

1. 一次提交围绕一项可说明的改动，写清解决的问题。
2. 提交前检查 `git diff` 和 `git status`，确认没有数据库、个人录音、凭证和临时文件。
3. 修改功能后运行相关检查。现有原型统一入口是 `python3 prototype/verify.py`，前端操作和音频播放另做浏览器检查。
4. 推送自己的分支并创建Pull Request，由另一位成员查看后合并。
5. PR说明写清改动、验证方式、未解决依赖，以及是否改变接口或数据结构。

尚未设置必须审批的分支规则，以上是组内协作方式。第一次导入的第一周快照直接提交至 `main`，后续功能开发按分支协作。

## 检查和证据

每个人负责自己模块的正常流程与错误流程。统计、删除、撤销和导出之间的关系需要一起检查。检查记录写实际运行过的内容，真实联调未完成时保留待完成状态。

`verify.py` 使用临时数据库，会刷新演示验证记录和导出ZIP。如果只是本地练习，不必把每次生成的时间差异提交。需要更新阶段证据时，说明运行版本与结果。

原型仅用于本机演示。接入真实学生数据之前，由项目统一确认权限、数据用途和存储方式。仓库中的测试数据保持匿名或合成样例，个人数据与密钥留在获授权的存储中。

## 阶段归档

阶段PPT、讲稿和进展摘要放入 `reports/week-XX/`。可复现的检查与截图放入 `evidence/`，不要把临时构建目录和运行数据库作为阶段成果提交。

第一周离线包由 `scripts/package_week01.py` 生成，当前用于保存2026年11月16日的第一周快照。后续阶段使用新的报告和包名，避免覆盖历史快照。
