# 上线执行手册：资源确定后按此部署

当前状态：管理端、同步接收器、回传日志、启动检查和本机 TLS 演练已提供。**正式服务器、域名、学生生产配置与真实数据授权未确定，不声称已经公网部署。** 此手册采用 Linux + systemd + Caddy，Windows 本机验收另见第三周说明。

## 一、需要最后补齐的配置

| 项目 | 谁确认 | 用途 |
|---|---|---|
| 服务器登录方式、资源规格、域名与 DNS | 闫晓奕与师兄/项目资源维护者 | 管理组执行部署，不依赖算法先完成 |
| 学生服务固定提交、启动命令、模型/资源要求、生产模式与 SMTP | 学生/算法组 | 学生身份与邮件、录音存储和算法运行 |
| 命题服务固定提交、题库版本、持久化目录与服务认证 | 命题组 | 命题工作区及覆盖回传 |
| 管理员/只读名单、录音授权范围和保留期限 | 三组共同确认 | 正式身份与真实数据使用 |

不得用本机 `run_demo.py` 作为生产启动器。它会初始化示例库并开启本机验证入口。学生源码当前把数据库固定在其 `backend/data` 下，部署升级必须保留该目录和音频目录；等学生组提供外置数据目录配置后再调整，不直接将只读代码发布目录用于学生持久化。

## 二、管理服务目录布局

```text
/opt/shengcai/releases/<固定提交>/     代码发布目录，保留回退版本
/opt/shengcai/current -> releases/... 当前代码链接
/opt/shengcai/venv/                   管理 Python 环境
/etc/shengcai/management.env          管理配置，root 读取，0600
/etc/shengcai/integration.env         交接任务专用令牌与地址，root 读取，0600
/etc/shengcai/accounts.json           actor/role/token_sha256；服务用户可读
/var/lib/shengcai/management/         管理 SQLite 和音频
/var/lib/shengcai/integration/        覆盖回传日志及锁
/var/backups/shengcai/                私有备份，与在线目录分开
```

由服务器维护者创建 `shengcai` 系统用户、上述数据目录并授予相应所有权；不以 root 运行应用。管理环境安装 `backend/requirements.txt`，先用 `requirements-dev.txt` 在部署机独立验收。学生和命题依赖按各组交付单独安装，避免互相覆盖。

`management.env` 采用 [配置清单](.env.example)，正式填写：

```text
ADMIN_AUTH_FILE=/etc/shengcai/accounts.json
ADMIN_DATA_DIR=/var/lib/shengcai/management
ADMIN_PUBLIC_ORIGIN=https://实际域名
ADMIN_COOKIE_SECURE=1
STUDENT_BASE_URL=http://127.0.0.1:8000
PROPOSITION_BASE_URL=http://127.0.0.1:8001
```

不要设置 `PORTAL_DEMO`。不同人使用不同 actor 和令牌；accounts.json 保存 SHA256，不把原始令牌写进仓库。管理服务继续只有一个 worker，当前会话内存不跨进程共享；重启后需要重新登录，业务数据不丢失。

## 三、检查并启动

服务模板中的 `/opt/shengcai/current` 和数据目录必须与实际布局一致。将 [management service](shengcai-management.service) 交给 systemd，先执行 `systemd-analyze verify` 检查目标机器支持的配置项，再启动。

```bash
sudo systemd-analyze verify /etc/systemd/system/shengcai-management.service
sudo systemctl daemon-reload
sudo systemctl enable --now shengcai-management.service
sudo systemctl status shengcai-management.service
sudo journalctl -u shengcai-management.service -n 100 --no-pager
```

`ExecStartPre` 自动运行 `deploy/preflight.py`：检查正式模式、HTTPS 来源、安全 Cookie、管理员配置、仓库外可写数据目录及两个服务地址。配置不完整会拒绝启动；输出不含令牌或配置原值。数据目录由部署者预先创建，检查不代建数据库。

只允许 Caddy 对外开放 80/443；管理 8766、学生 8000、命题 8001 均只监听回环。跨机器部署时配置 HTTPS 及对应认证，不能直接将未鉴权命题写接口暴露公网。

## 四、配置 HTTPS

把 [Caddyfile.example](Caddyfile.example) 的占位域名替换为实际域名，再执行：

```bash
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
```

模板已用 Caddy 2.11.9 校验；本机另用临时证书演练 HTTPS 和安全 Cookie，没有修改系统证书信任。正式公网证书仍需实际 DNS、可达的 80/443 和可持久写入的 Caddy 数据目录，见 [Caddy 官方 HTTPS 条件](https://caddyserver.com/docs/automatic-https)。校验命令不等于申请证书或完成上线，见 [官方配置校验说明](https://caddyserver.com/docs/command-line#caddy-validate)。

在与服务相同的配置环境中运行 `python deploy/preflight.py --live --output /私有路径/preflight.json`，检查 HTTPS 健康接口、匿名管理请求 401 和两端服务健康。工具不自动读取 `.env`；由进程管理器注入环境。再从另一台设备验证页面、登录、麦克风、上传、Range 回放、导出，不能只测服务器自己访问自己。

## 五、启用持续对接（取得真实接口后）

先手动运行，通过后才启用对应 timer。`integration.env` 需要独立管理身份令牌 `ADMIN_TOKEN`、已确认的 `STUDENT_SERVICE_TOKEN`、`STUDENT_SOURCE_ID`、`STUDENT_FEED_PATH`、两个服务地址及命题认证（若启用）。这些变量只保存在服务器私有配置。

```bash
python sync_worker.py --admin http://127.0.0.1:8766 student --student http://127.0.0.1:8000 --source-id 已确认来源 --feed-path /已确认变更接口
python sync_worker.py --admin http://127.0.0.1:8766 coverage --proposition http://127.0.0.1:8001 --state-file /var/lib/shengcai/integration/coverage.sqlite3
```

[学生同步 service](shengcai-student-sync.service) 与 [timer](shengcai-student-sync.timer)、[覆盖回传 service](shengcai-coverage.service) 与 [timer](shengcai-coverage.timer) 均已准备，成功安装后每次结束一分钟再执行下一次。未交付接口前不启用；当前并未替用户在任何服务器安装定时器。

发生冲突：任务返回非零并保留进度，检查 `journalctl -u 对应服务`、管理端来源游标和覆盖日志的 pending/received 状态；不要删除状态库或跳过失败批次。管理端游标包含在管理备份中，覆盖日志独立保存在 integration 目录，备份时停止相关 timer/service 后复制其 SQLite 日志；不要复制正在写的 SQLite 主文件而漏掉 WAL。

systemd 模板限制写入目录，依据 [官方执行环境说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)。模板尚未在分配的正式 Linux 主机启动，主机检查与实际运行是上线步骤，不用文本存在代替测试通过。

## 六、备份、恢复与回退

1. 用 `maintenance.py backup 数据目录 新备份目录` 做在线一致性备份，再 `verify`。本轮已验证同步游标、事件去重、管理备注和音频一起恢复。
2. 恢复使用 `maintenance.py restore 备份目录 全新恢复目录`，绝不覆盖当前库。
3. 暂停写入和交接任务，停止管理服务，修改数据目录指向恢复库，启动并核对健康、统计、历史、音频、游标、导出。旧库保留。
4. 代码回退时停止管理服务，将 current 指回上一个固定提交，再启动。跨数据库迁移不能只回退代码；先保留新库，按已验证备份恢复，不能把新旧写入直接混合。
5. 备份来自较旧时间时，管理游标和命题已接收快照可能不一致。与上游确认补发区间及覆盖实例切换后再启用定时器，不能强行发送旧覆盖快照。
