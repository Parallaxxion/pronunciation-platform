## 项目简介

以下摘自老师的[《任务书—音频数据采集系统 V6.4》](05_相关材料/项目任务书/任务书-音频数据采集系统-V6.4.docx)：

> 本期的任务是完成系统的学生子系统、命题子系统、管理端子系统的建设与集成，以实现音频数据采集：命题子系统产出分级跟读题库并提供题目抽取接口，学生子系统面向留学生完成注册、看题、录音与上传，并通过内置的基线诊断算法实现偏误自动检测；管理端子系统负责数据统计、核查与导出；音频数据按统一格式存档，供后续标注与算法训练使用。

本仓库对应上述第一阶段，后续阶段以老师另行发布的任务为准。

| 小组 | 第一阶段主要职责 | 交付与对接 |
|---|---|---|
| 学生端 | 注册与同意授权、按级看题、录音和上传、保留重录、基线偏误检测 | 接收命题题目；向管理端提供授权范围内的录音、元数据与诊断结果 |
| 命题端 | 分级题库；出题→校验→统计→补题→达标发布的流水线 | 向学生端提供已发布题目；结合录音覆盖情况改进抽题 |
| 管理端 | 数据管理、统计、录音核查、诊断展示、可撤销操作与导出 | 牵头三端整合、统一前端风格、协调数据契约和验收 |

老师第二周强调：命题端同时交付高质量分级题库；管理端加强整体整合；三端前端统一风格。我们以现有管理端 UI 为共同视觉基准，各组完善自身业务。学生页面本期不展示诊断结果，管理页面负责核查。

11月25日更新：已完成[两套风格的三端统一 Web](03_管理端/当前开发/web/README.md)，可在本机运行青绿版和学院蓝版；[交付与测试记录](03_管理端/2026.11.23-2026.11.29第3周/三端Web交付与验证_20261125.md)与[跨组待交接清单](03_管理端/2026.11.23-2026.11.29第3周/其他两组待交接清单_20261125.md)已更新。命题 11 月 25 日完整固定源码及材料在[命题第三周归档](02_命题端/2026.11.23-2026.11.29第3周/README.md)。当前为本机联调版，正式部署、真实算法与跨端数据闭环仍待联合验收。

### 4. 每天如何开发与提交

先保存未提交的个人修改，再更新主分支并创建自己的功能分支：

```bash
git switch main
git pull --ff-only
git switch -c feat/student-question-integration
# 修改自己负责的文件，完成检查后逐项添加
git add 01_学生端/当前开发/backend/app/routes/questions.py
git commit -m "接入统一题目来源"
git push -u origin feat/student-question-integration
```

以上是学生端示例；其他组换成自己的分支名和文件路径。随后在总仓库发起 Pull Request（PR），写清周次与序号（例如“第2周第6项”）、改动、接口影响、测试结果和阻塞项，请另一位相关成员核对后合并。

有写权限的成员推送自己的分支；没有写权限的成员可 fork 本公开总仓库，再向本仓库提交 PR。写权限需维护者按实际名单安排，目前没有自动邀请成员或设置强制分支保护。

如果某组暂时仍在原仓库工作，交接时提供来源 commit 和变更清单，由总仓库通过 `import/…` 分支比对合入。**不要整目录覆盖已修改的代码。** 当前不存在两个仓库之间的自动双向同步；每个任务开始时明确在哪个仓库开发。

| 入口 | 用途 |

**两份内容均已开放链接阅读、编辑，无需申请权限。** 如飞书提示登录，使用自己的账号登录即可。当前打开「第3周（11.23—11.29）」，第二周保留原记录。每周是一张独立分表，旧周保留，不把所有周次放进同一张长表。

每张周表固定六列：

| 列名 | 填写方法 |
|---|---|
| 序号 | 本周从1开始顺延；一行一件需求，已有序号不随排序改变 |
| 需求组 | 谁提出需求，例如学生组、命题组、管理组或三组共同 |
| 承接组 | 谁负责答复或提供成果；两组配合时直接写清，不另设个人负责人列 |
| 需求 | 需要什么、用途、怎样算满足；双方确认的完成时间也可写在这里 |
| 答复和验收成果 | 承接组填写答复、成果链接、PR／commit、验证步骤与实际结果；未完成时写明缺少什么及下一步 |
| 验收确认 | 需求组检查后填写“待确认／通过／需补充”，可补确认日期和原因 |

1. **选周并提需求**：先查看本周是否已有相同需求，再按序号新增一行，填写需求组、承接组和需求内容。
2. **答复和交付**：承接组在同一行持续更新答复及成果，双击记录可查看长文本。涉及接口时，先核对[接口对齐报告](04_接口说明/接口对齐报告.md)，相关组确认后通过 PR 更新 `04_接口说明/`。
3. **确认验收**：需求组按约定检查成果，再填写最后一列。提供了链接或通过本地检查不等于已经由需求组验收。
4. **新一周接续**：复制分表时只保留字段结构和视图设置，改成新周名称。需要继续对接的事项写明“承接第2周第6项”等来源，旧周注明转入哪一周，新周序号仍从1开始。
5. **会议与归档**：会议结论和 GitHub PR 统一引用“第几周第几项”。会议纪要按日期写入手册第七节；周末把已验收成果、关键结论及提交链接写回本组周次 README，模板见手册第八节。

第2周已迁入14项初始需求。11月23日核查时全部验收确认仍为待确认，实际答复和已有成果写在对应行。后续由三组共同补充，不代替其他组确认验收或时间。

飞书维护日常需求、答复和验收；GitHub 保存正式代码、接口规范、测试证据和每周成果。历史协作模板仍可在 Git 提交中追溯，仓库不再维护另一份动态台账。

### 6. 每周如何留存成果

每组使用 **`YYYY.MM.DD-YYYY.MM.DD第N周`** 命名。当前按 11 月 9 日任务发布周起算：第一周 11.09–11.15，第二周 11.16–11.22，第三周 11.23–11.29。此为仓库整理规则，**不代表老师已确认最终截止日**。

- `当前开发/`：持续修改的代码；每周不搬家、不改运行路径。
- 周次目录：放当周 README、汇报材料、测试证据和需要留存的成果快照。
- 每周 README 写清：完成了什么、负责人、对应总仓库 commit/PR、运行与验证、尚未完成、下周计划。
- 周末归档前先去掉运行数据库、真实录音、密钥、虚拟环境和缓存；归档后保留原文件，补充说明另写文件。

在总仓库根目录执行：

```bash
python -m unittest discover -s 04_接口说明/联调工具/tests -v
python 04_接口说明/联调工具/scripts/check_algorithm_kit.py
```
