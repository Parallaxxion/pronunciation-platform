# 管理端组员接手指南

先用约30分钟完成一次原型体验，再开始改代码。当前原型是AI辅助编程生成的初版，接手时需要理解自己的模块及验证结果，真实数据接入后继续检查。

## 三人共同完成的首次体验

在仓库根目录启动 `python3 prototype/server.py --open-browser`，Windows 使用 `py -3`。依次完成：

1. 认识初始4名虚构说话人、4道题、5条录音，确认目标3条只是演示参数。
2. 搜索 `S-001`，查看同一学生的两次录音。
3. 打开 `R-001`，回听音频，观察字上偏误和字间增读。
4. 保存备注后重新打开，确认内容仍在。
5. 删除一条录音，查看统计变化，再从已删除列表恢复。
6. 导出ZIP，打开清单和标注，按 `recording_id` 找到对应音频。
7. 运行 `python3 prototype/verify.py`，查看15项检查结果。

每位成员都应能说明：管理端接收什么数据、对数据做什么、导出给谁，以及原型还有哪些未完成内容。

## 周佳怡的起点

主责是管理界面与录音核查，细节见[完整分工](分工与验收清单.txt)。

先读 `prototype/static/index.html` 的页面骨架、`style.css` 的样式，以及 `app.js` 中的 `render`、`renderRows`、`showDetail`、`mutate`。这些函数分别处理导航渲染、筛选列表、录音详情和写操作调用。

下一步先列出页面需要的字段和异常状态，与闫晓奕对齐，再补用户/题目管理表单和真实诊断状态。每次修改至少体验对应正常流程和一个失败流程。字间增读、句首句尾、同字多个错误要有明确例子。

统计与导出页面由王阳开发，公共样式与组件一起协调。

## 闫晓奕的起点

主责是核心数据、可撤销操作与三端对接。

先读 `server.py` 中的 `initialize`、`records`、`Handler.do_GET`、`Handler.do_POST`，以及[接口草案](../api/三端接口与数据契约草案.txt)。理解四张演示表、外键关系、`version` 和操作历史。

下一步明确两端对接人、数据归属与写入权限，确认一条题目、录音及诊断样例。补齐数据管理时同时定义撤销行为，保证题目变更不会让历史录音失去来源。

为周佳怡提供明确的查询和写操作约定，为王阳明确统计所需状态和数据访问方法。

## 王阳的起点

主责是统计与数据导出，包含这两块的接口和页面。

先读 `server.py` 中的 `export_archive`、`/api/state` 查询，`app.js` 中的采集概览和题目覆盖，以及 `verify.py` 的ZIP核对部分。

下一步列出统计口径：注册人数、已有录音人数、重录、重试上传、已删除录音、合格录音怎样处理。按一份可手工计数的小样本验证结果，并补齐文件缺失、导出失败等提示。

导出要能通过录音编号关联音频、元数据和偏误，原始音频与WAV根据上游真实文件处理。部署说明由王阳牵头整理，服务权限、HTTPS与页面访问由三人一起验证。

## 第一次协作对齐要留下的结果

- 三人的熟悉技术和可投入时间。
- 最终技术栈决定及依据，或者仍需师兄确认的具体问题。
- 公共数据字段、文件边界和第一版内部接口。
- 首次内部联调时间和首次真实三端联调时间。
- 每个人下一次提交中可以演示的具体成果。

当前 `server.py` 和 `app.js` 都集中了多个模块。正式多人开发前先约定拆分方式，每次改公共文件时说明修改区域，避免互相覆盖。
