音频数据采集系统 第一阶段任务要求与实施说明
整理日期：2026年11月9日
用途：全面理解本阶段实验与开发任务，暂不进行人员分工。

一、先理解本阶段到底要做什么

本阶段要完成一个可实际使用的音频数据采集系统，由学生子系统、命题子系统、管理端子系统组成，并将三者集成。

完整业务流程：
按等级建设合格题库 → 题目入库 → 学生注册并同意录音用途 → 选择等级并抽题 → 显示文本和逐字拼音 → 学生录音、试听、重录、上传 → 保存原始音频并统一转成WAV → 基线算法自动检测偏误并存档 → 管理端统计、回听、查看偏误 → 导出音频、信息清单和偏误标注。

最终目的：为后续人工标注与算法训练积累格式统一、可追溯的录音数据。
本次不是整个中文发音智能诊断与评价系统的完整开发任务；后续阶段另行安排。但“基线诊断算法”已经是本阶段必做内容，不能全部留到后续。

三、学生子系统的明确要求

面向留学生，负责从注册到录音上传的采集交互。

1. 注册与隐私
   收集国籍、母语、汉语水平等背景信息。
   注册必须绑定邮箱；任务书没有明确规定必须采用哪一种邮箱验证方式。
   注册页说明录音数据用途，可链接独立隐私协议；必须同意后才能注册。
   为每名学生分配匿名编号；录音数据不与真实姓名关联。

2. 获取题目
   按《国际中文教育中文水平等级标准》组织题库。
   学生选定等级后，调用命题子系统抽取接口。
   优先抽取没有录音或录音较少的题目，让采集覆盖趋于均衡。

3. 展示题目
   同时显示题目文本与逐字拼音。
   “有一整句拼音字符串”不等于已经实现逐字对应展示，需要处理字与音节的对应关系。

4. 录音
   一键开始，支持试听与重录。
   每次录音均保留，不能只保存最后一次或直接覆盖先前录音。

5. 上传与断网处理
   录音完成后上传。
   网络中断时本地暂存，网络恢复后自动补传。

6. 存储
   统一转码为WAV，同时保留原始录音文件。
   每条录音配一条元数据：说话人匿名编号、题目编号、录音序号、录音时间、设备信息。

7. 诊断结果的使用范围
   上传后自动诊断并存档。
   本期学生端不展示诊断与评分结果。
   诊断用于管理端查看和后续标注复核，按演示系统的逐字偏误样式呈现。

四、基线诊断算法的明确要求

这部分归在学生子系统章节中，但其结果主要给管理端和后续标注使用。

1. 部署中文语音识别模型，例如任务书提到的Whisper、wav2vec 2.0等开源模型。
2. 录音提交后，自动得到带声调的拼音序列。
3. 将识别拼音与题目逐字拼音进行声母、韵母对齐。
4. 检测并定位四类偏误：
   声韵母误读：在出错字上标注类型和实际读音。
   声调偏误：在出错字上标注类型和实际读音。
   漏读：在未读出的字上直接标记。
   增读：在两字之间标注多读出的音节。
5. 偏误结果随录音样本一起保存，作为机器预标。
6. 用含已知偏误的测试录音验收，检测类型和位置必须正确。

实施提醒（技术分析，不是老师新增要求）：
普通转写文本与实际发音偏误不是同一个信息。不能仅把识别出的汉字转换为标准拼音，就认定已经可靠识别了实际声调或声韵母错误。需要尽早用故意错读的录音验证所选方案能否保留这些差异。
算法不必从零训练一个完整评测模型，但必须形成可运行、可验收的四类偏误检测流程。

五、命题子系统的明确要求

面向命题人员，按各等级字表与语法点建设跟读题库，并提供抽题服务。

1. 每一级都执行闭环工作流
   出题 → 校验 → 统计 → 按缺口补题 → 再校验、再统计，直至达标后入库。

2. 出题
   只使用对应等级允许的字与语法点。
   句子口语化、场景真实，长度符合该等级约束。
   题目正文不用阿拉伯数字与拉丁字母。

3. 校验
   检查字表越界、句长越界、语法点命中、编号重复、文本重复。
   不合格题修改或剔除，直到零不合格。

4. 统计与补题
   统计字覆盖率、字频、语法点频次。
   按缺口清单补题并复跑，统计达标后入库。

5. 每题的数据
   至少包含编号、等级、文本、逐字拼音、语法点标注。

6. 抽取接口
   支持按等级抽取。
   支持参考历史录音覆盖程度，优先返回尚无录音或录音较少的题。
   返回题目文本及逐字拼音；题目入库后即可被学生端取得。

六、参考命题包已提供什么，还缺什么

以下属于提供的参考包现状，不代表项目系统已经验收通过。

1. 已提供一级示例
   final.json含256题。
   附带最终校验报告记录：256题合格，0题不合格，无重复编号及文本。
   附带最终统计报告记录：300字全部覆盖，41个语法点全部覆盖，结论达标。
   README记录核心字每字至少3次、语法点每点至少2次。
   这些是随包报告，本次整理未执行脚本重新验算。

2. 一级参考配置
   句长3至12个汉字，标点不计。
   题量目标110至280题。
   字覆盖率阈值90%，语法覆盖率100%。
   核心字每字至少3次，语法点每点至少2次。
   这是一级参考配置，不能直接当成所有等级的统一要求。

3. 已提供脚本与记录
   build_level1.py：生成一级等级配置。
   validate.py：逐题校验。
   stats.py：统计覆盖与频次。
   pipeline.py：串联校验、统计及合并题库。
   reports保存历轮校验、统计和补题计划。

4. 需要继续完成的工作
   包内尚未提供二至九级等级数据文件。
   需要把脚本工作流、数据入库与系统接口衔接起来。
   需要实现面向命题人员的实际操作方式、题库管理与学生端抽题服务。
   示例pinyin使用整句字符串，包含连写词，需要整理为可逐字对齐的表示。
   配置中的source_note说明字表是参照标准整理，仍需对照官方标准核验；不宜仅凭脚本通过就认定与正式标准逐字一致。

5. 参考Skill的人工检查建议
   正则只能初筛语法命中，仍需人工核查教学意义上的语法使用与拼音正确性。
   Skill建议每轮抽检10%，重点检查复杂语法声明。
   10%是参考建议，不是任务书单独规定的验收比例。
   Skill中扩展声韵调覆盖、对话与短文题型等属于扩展方向，不是本期已经明确要求全部完成的内容。

七、管理端子系统的明确要求

面向管理员与研究人员。

1. 对接各子系统后台，对用户、题目、录音样本等数据增删改查。
2. 展示注册人数、各等级与各题收录量、缺口分布，实时反映采集进度。
3. 按学生或按题目查看录音明细，并在线回听。
4. 每条录音能追溯到说话人编号、题目编号、录音序号。
5. 同步查看基线诊断结果，展示逐字和字间偏误标注。
6. 一键导出全部音频、对应信息清单、逐字偏误标注结果。
7. 数据增删改查实际生效且可撤销。
8. 统计结果与实际数据一致；导出包可被脚本直接读取，并可用于后续标注、训练。

八、部署与系统集成要求

1. 网页端交付，暂不开发移动应用。
   注意：任务书此处写“两个子系统均以网页端交付”，但全文实际列出三个子系统，存在数量表述不一致。实施时建议按三个子系统都可通过网页使用规划，向老师确认命题端具体交付形式。
2. 系统部署在HTTPS环境，开发早期就做真机录音验证。
   不应等到最后才确认真实设备能否授权麦克风、录音和上传。
3. 保证统一音频格式与元数据可追溯。
4. 全链路实测：命题入库 → 按等级抽题 → 录音上传 → 基线诊断 → 管理端导出。
5. 先小范围试用，修复问题后再扩大采集。

九、实验与验收检查清单

下列检查对应任务书验收要求；具体操作是建议的测试办法。

[ ] 学生注册：邮箱绑定、背景信息保存、隐私未同意不能注册、生成匿名编号。
[ ] 抽题：各等级返回范围正确，无录音和少录音题目得到优先采集机会。
[ ] 题面：文本与拼音逐字对应，检查多音字、轻声及标点处理。
[ ] 录音：在HTTPS真实设备上完成授权、录制、试听、重录；多次录音均能查到。
[ ] 补传：模拟断网，验证录音本地保留、网络恢复后自动上传；建议另查重复补传问题。
[ ] 文件：原始文件保留，WAV可正常播放，每次录音都有规定的元数据。
[ ] 偏误检测：分别准备已知声韵母误读、声调偏误、增读、漏读录音，核对类型与位置。
[ ] 诊断展示：错字位置、实际读音、漏字与字间增读清楚；学生端不显示诊断或评分。
[ ] 命题：运行每级题库的校验和统计，零不合格且覆盖达标，报告可查。
[ ] 管理：用户、题目、录音数据可管理，修改和删除等操作可撤销。
[ ] 统计：人工抽查数据库与界面数量、缺口数据一致。
[ ] 核查：按学生和题目都能定位并回听录音，关联正确。
[ ] 导出：音频、信息清单、偏误标注齐全，用脚本读入并核对关联。
[ ] 集成：用真实数据完整跑一遍从命题入库到导出的流程。
[ ] 试点：记录小范围试用问题，修复后再扩大采集。

十、建议实施顺序 暂不分工

第一步：确认范围与数据约定。
把用户、题目、录音、偏误结果之间的关系理清；统一匿名编号、题号、录音序号、逐字拼音和导出格式。列出尚需老师确认的问题。

第二步：尽早验证两个关键难点。
一是HTTPS真机录音、上传和转码；二是已知错读录音能否被基线方案正确定位。优先暴露录音兼容与算法可行性问题。

第三步：用一级示例打通一个完整流程。
先导入少量已核对的题，完成注册、抽题、录音上传、文件保存、诊断、后台查看与导出。此时只验证流程，不代表达到全部等级要求。

第四步：补齐完整功能。
完善命题闭环、其他所需等级、均衡抽题、断网补传、全部录音保留、管理操作撤销、统计和结构化导出。

第五步：按验收清单测试并小范围试用。
保存测试录音、预期结果、实测记录及问题修复记录，完成全链路验证后再扩大采集。

十一、最终应形成的成果

任务书明确要求的成果：
可部署并使用的学生、命题、管理三个子系统及其集成流程；达标题库及抽题接口；可运行的基线诊断流程；规范音频及元数据；可直接供后续处理使用的导出包；逐项功能与全链路实测通过。

建议同时准备、便于演示验收的材料（不是任务书新增的硬性交付格式）：
系统使用与部署说明、数据库和接口说明、题库校验统计报告、已知偏误测试集、验收记录、小范围试用问题清单。

十二、需要向老师确认、但不妨碍先做原型的问题

1. 本期必须覆盖全部一至九级，还是允许先验收指定等级？任务书强调各级题库，参考包仅有一级，不能擅自把最终范围缩为一级。
2. “两个子系统网页端”是否应理解为三个子系统均需网页入口？
3. 各等级的正式字表、语法点、句长、覆盖阈值、题量和实际采集量如何确定？一级参考值不能套用全部等级。
4. 统一WAV的采样率、位深、声道数，以及原始文件、元数据、偏误标注的最终导出结构是否另有约定？任务书尚未明确这些细节。
5. 四类偏误检测采用什么规模的测试集、准确性指标与通过门槛？任务书要求类型与位置正确，但没有给量化阈值。
6. 部署资源、试点规模、截止日期及最终提交方式是什么？现有任务书与群通知没有给出这些具体安排。

十三、一句话理解自己的工作

现在需要做的是一套能规范采集留学生中文朗读音频、自动生成初步偏误标记、并让研究人员核查和导出数据的网页系统。先理解数据如何流转，优先打通一条完整链路，再补齐各模块和验收要求；现阶段无需先做人员分工。
